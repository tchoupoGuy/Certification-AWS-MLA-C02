# 3.3 — Implémenter l'orchestration automatisée et les pipelines CI/CD pour MLOps et IA

Task statement officiel MLA-C02 : *Task 3.3: Implement automated orchestration and continuous integration and continuous delivery (CI/CD) pipelines for MLOps and AI workloads.* Onze skills (3.3.1 à 3.3.11) — le task statement qui gagne le plus de skills bruts après 3.2 (cinq ajoutés : gestion de prompts, pipelines d'agents, tests de modèles IA, versioning de FM fine-tunés, orchestration RAG/knowledge base).

## En une phrase

Automatiser tout ce qui, jusqu'ici, se faisait à la main (tester, déployer, ré-entraîner, versionner) — pour qu'un changement de code ou de données déclenche le bon pipeline sans intervention humaine à chaque étape.

## Analogie

C'est le seul task statement du Domaine 3 où le cahier a maintenant un vrai ancrage direct : `.github/workflows/ci.yml` (predict-student-dropout, ajouté ce mois-ci) fait tourner `pytest` automatiquement à chaque push, sur deux jobs séparés (service Flask, pipeline d'entraînement) — exactement 3.3.4 (tests automatisés dans un pipeline CI/CD). C'était d'ailleurs identifié comme un manque explicite dans `BILAN-ENTREPRISE.md` avant d'être corrigé. Ce qui reste absent : tout le reste du pipeline CI/CD AWS-natif (CodePipeline/CodeBuild/CodeDeploy), le déploiement automatique après des tests verts (CD, pas seulement CI), le ré-entraînement automatique, et tout ce qui touche aux FM/agents (gestion de prompts, versioning de modèles fine-tunés).

## Vocabulaire

| Terme AWS | Définition simple | Point de repère (cahier ou équivalent connu) |
|---|---|---|
| **AWS CodePipeline** | Orchestre les étapes d'un pipeline CI/CD (source → build → test → déploiement) | Le rôle que joue `.github/workflows/ci.yml`, mais côté AWS natif plutôt que GitHub Actions |
| **AWS CodeBuild** | Exécute des étapes de build/test dans un environnement managé | Le job GitHub Actions qui lance `uv sync && uv run pytest` — même rôle, exécuteur différent |
| **AWS CodeDeploy** | Automatise le déploiement (rolling, blue/green, canary) vers des instances/conteneurs/Lambda | Aucun équivalent — le déploiement de predict-student-dropout reste manuel (`docker build` + `docker run` lancés à la main) |
| **AWS CodeCommit / CodeConnections** | Dépôt Git managé par AWS / connexion à un dépôt externe (GitHub, etc.) pour déclencher un pipeline | `CodeConnections` est l'équivalent exact du lien GitHub→Actions déjà en place — un pipeline CodePipeline pourrait se déclencher sur le même repo GitHub via CodeConnections plutôt que CodeCommit |
| **Rollback automatisé** | Revenir automatiquement à la version précédente si un déploiement échoue ou dégrade une métrique | Aucun équivalent — rien n'annule un déploiement raté dans le projet |
| **Blue/green, canary deployment** | Déployer une nouvelle version en parallèle de l'ancienne (blue/green) ou sur une petite portion du trafic d'abord (canary), pour limiter le risque | Aucun équivalent — le projet n'a qu'une seule version active à la fois |
| **SageMaker Model Registry / MLflow** | Cataloguer et versionner les modèles entraînés, avec leur statut (en test, approuvé, en production) | Aucun équivalent — `best_model.joblib` est un fichier unique, écrasé à chaque nouvel entraînement, sans historique de versions |
| **Amazon Bedrock Prompt Management** | Versionner et gérer les prompts envoyés à un FM comme des artefacts à part entière | Aucun équivalent — les prompts de Projet_04/07/08 sont écrits en dur dans le code, jamais versionnés séparément |
| **Ré-entraînement automatisé** | Un pipeline qui relance l'entraînement automatiquement (sur un calendrier, ou quand une dérive est détectée) | Aucun équivalent — `main.py` (training) se lance uniquement à la main |

## Comment ça marche en détail

Un pipeline CI/CD complet enchaîne plusieurs étapes automatisées : le code (ou les données, ou un prompt) change → un test automatique valide le changement (CI, ce que `ci.yml` fait déjà) → si les tests passent, un déploiement se déclenche (CD, ce qui manque encore) → le déploiement suit une stratégie qui limite le risque (rolling, blue/green, canary) plutôt qu'un remplacement brutal → si une métrique se dégrade après déploiement, un rollback automatique revient à la version précédente. Le point clé à retenir pour l'examen : CI (tester automatiquement) et CD (déployer automatiquement) sont deux étapes séparées et souvent confondues — avoir l'une ne garantit pas l'autre. predict-student-dropout a la première, pas la seconde.

Pour MLOps spécifiquement, ce pipeline s'applique aussi à l'entraînement lui-même, pas seulement au code applicatif : un pipeline peut se déclencher automatiquement quand de nouvelles données arrivent, ré-entraîner le modèle, l'évaluer (Domaine 2.3), et ne le promouvoir en production QUE s'il dépasse le modèle actuel sur les métriques suivies — c'est le rôle de SageMaker Model Registry, qui trace quelle version de modèle est "approved" et déployable, par opposition à une simple écriture de fichier `.joblib` qui écrase silencieusement la version précédente.

Pour les FM et agents, l'automatisation couvre des artefacts différents : un prompt versionné (Bedrock Prompt Management) peut être testé comme du code (3.3.9 — tester qu'un changement de prompt n'a pas dégradé la qualité des réponses), un agent peut être déployé et versionné indépendamment du FM sous-jacent (3.3.8), et une Knowledge Base RAG a besoin de son propre cycle de rafraîchissement automatisé (3.3.11 — quand les documents sources changent, ré-indexer sans intervention manuelle).

## Un exemple annoté

```yaml
# predict-student-dropout, .github/workflows/ci.yml — CI réel, déjà en place :
jobs:
  test-service:
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v3
      - run: uv sync --frozen
      - run: uv run pytest
# Ce que ça fait : valide AUTOMATIQUEMENT chaque push. Ce que ça NE fait PAS :
# rien ne se passe après un test vert — pas de build d'image Docker, pas de
# push vers un registre, pas de déploiement. Un vrai pipeline CD ajouterait,
# après "uv run pytest" réussi :
#   - build + push de l'image Docker vers Amazon ECR
#   - déclenchement d'un déploiement (CodeDeploy, ou mise à jour d'un endpoint
#     SageMaker si le modèle lui-même a changé) avec une stratégie qui limite
#     le risque (par exemple, ne basculer que 10% du trafic d'abord).
```

## Ancrage : predict-student-dropout

`BILAN-ENTREPRISE.md` documente explicitement ce gap dans sa liste "Pour aller plus loin" : la CI existe, la CD reste hors périmètre ("nécessiterait de provisionner une vraie infra cible"). C'est un exemple honnête et rare dans ce genre de projet : la limite n'est pas cachée, elle est écrite noir sur blanc avec la raison précise (pas d'infra AWS cible provisionnée, voir Domaine 3.2) — exactement le genre de justification qu'un examinateur MLA-C02 attendrait dans une vraie prise de décision d'architecture.

## Pièges classiques

- **CI vs CD** : un scénario qui décrit "les tests se lancent automatiquement mais quelqu'un déploie encore à la main" décrit un pipeline CI SANS CD — piège classique de répondre "le pipeline CI/CD est complet" alors qu'une des deux moitiés manque.
- **Blue/green vs canary** : blue/green bascule TOUT le trafic d'un coup vers la nouvelle version (mais garde l'ancienne prête en cas de rollback) ; canary bascule PROGRESSIVEMENT (10%, puis 50%, puis 100%). Si l'énoncé mentionne un pourcentage croissant de trafic, c'est canary.
- **CodeCommit vs CodeConnections** : CodeCommit est un dépôt Git hébergé PAR AWS ; CodeConnections connecte un pipeline AWS à un dépôt EXTERNE (GitHub, GitLab...) — pour un projet déjà sur GitHub (comme predict-student-dropout), c'est CodeConnections, pas une migration vers CodeCommit.
- **Model Registry vs simplement sauvegarder un fichier modèle** : la question type oppose un scénario où plusieurs versions de modèles doivent être comparées/auditées dans le temps (Model Registry) à un cas où un seul modèle suffit sans historique — `best_model.joblib` (écrasé à chaque run) est l'exemple exact de ce qui MANQUE de Model Registry.
