# 3.1 — Gérer l'infrastructure de déploiement pour les types de modèles ML/IA

Task statement officiel MLA-C02 : *Task 3.1: Manage deployment infrastructure for ML and AI model types.* Huit skills (3.1.1 à 3.1.8). Un point retiré depuis MLA-C01 (l'optimisation pour edge devices via SageMaker Neo), quatre ajoutés — tous centrés sur les FM et les agents : options de déploiement de FM (3.1.4), importer un modèle entraîné hors AWS (3.1.5), déployer des agents (3.1.6), configurations RAG (3.1.8).

## En une phrase

Une fois le modèle entraîné (Domaine 2), il faut décider comment et où il va répondre aux requêtes — et ce choix dépend presque entièrement du profil de trafic attendu (constant, sporadique, ou par lots).

## Analogie

C'est le domaine où predict-student-dropout est le plus avancé du cahier entier : `app.py` sert le modèle via Flask + Gunicorn, conteneurisé avec Docker, exactement le travail que 3.1 demande de raisonner en termes AWS. `BILAN-ENTREPRISE.md` documente même explicitement la progression (serveur de dev Flask → Gunicorn en production) — un cas réel de décision d'infrastructure de déploiement, avec sa justification écrite noir sur blanc. Ce qui manque : jamais comparé à un déploiement serverless ou asynchrone, jamais mesuré en coût/latence face à ces alternatives — Flask+Gunicorn est la SEULE option jamais envisagée dans le projet.

## Vocabulaire

| Terme AWS | Définition simple | Point de repère (cahier ou équivalent connu) |
|---|---|---|
| **Endpoint temps réel** (SageMaker real-time endpoint) | Instance(s) toujours allumée(s), répond en millisecondes, facturé en continu | Exactement ce que fait `app.py` + Gunicorn en continu — le service ne s'arrête jamais entre deux requêtes |
| **Endpoint serverless** (SageMaker Serverless Inference) | Aucune instance allumée en permanence, démarre à la requête, facturé à l'usage | Aucun équivalent — Gunicorn tourne en continu qu'il y ait du trafic ou non, contrairement à ce mode |
| **Endpoint asynchrone** (SageMaker Asynchronous Inference) | Met la requête en file d'attente, traite quand les ressources sont dispo, notifie le résultat plus tard | Aucun équivalent — `POST /predict` de predict-student-dropout répond toujours immédiatement (synchrone) |
| **Batch Transform** | Traite un gros volume de données en une seule fois, sans endpoint permanent | Aucun équivalent — jamais de scénario "prédire pour 10 000 étudiants d'un coup" dans le projet |
| **Multi-model / multi-container endpoint** | Plusieurs modèles servis par le même endpoint, chargés à la demande | Aucun équivalent — un seul modèle (`best_model.joblib`) servi par le service |
| **Bedrock Custom Model Import** | Importer un modèle fine-tuné en dehors d'AWS (ex. Hugging Face) pour le servir via Bedrock | Pertinent pour un modèle `sentence-transformers` local (Projet_04/07/08) si on voulait le servir via Bedrock plutôt qu'en local |
| **Agent (Bedrock Agents)** | Un FM qui peut appeler des outils/API et enchaîner des étapes pour accomplir une tâche | Projet_07 (`src/agent/planner.py`, `booking.py`, `pricing.py`) EST déjà un agent — orchestré à la main plutôt que via Bedrock Agents |
| **SageMaker Neo** | Compile un modèle pour tourner efficacement sur un device edge (hors cloud) | Retiré de MLA-C02 — utile de le savoir pour ne pas s'y attarder à tort |

## Comment ça marche en détail

Le choix entre les quatre modes d'inférence dépend du profil de trafic, pas de la qualité du modèle. **Temps réel** : trafic constant et prévisible, latence critique — le mode que Flask+Gunicorn reproduit déjà pour predict-student-dropout (un étudiant soumet un formulaire, attend une réponse immédiate). **Serverless** : trafic sporadique ou imprévisible, où payer pour une instance allumée 24/7 serait un gaspillage — pertinent si predict-student-dropout n'était utilisé que quelques fois par jour par un petit établissement. **Asynchrone** : la requête peut attendre (quelques secondes à quelques minutes), utile quand l'inférence elle-même est lourde (un gros modèle, une image haute résolution) et qu'il ne faut pas bloquer l'utilisateur en attendant. **Batch Transform** : pas de notion de "requête individuelle" du tout — prédire pour tout un dataset d'un coup, typiquement en tâche de fond planifiée.

Pour les FM spécifiquement, deux options s'ajoutent : utiliser Bedrock directement (le FM tourne dans l'infrastructure gérée par AWS, aucun endpoint à soi) ou déployer un FM sur un endpoint SageMaker dédié (plus de contrôle, notamment pour un modèle fine-tuné ou importé depuis l'extérieur via Custom Model Import). Le déploiement d'agents (3.1.6) ajoute une couche supplémentaire : un agent n'est pas juste "un modèle qui répond", c'est un système qui peut appeler plusieurs outils en séquence — Projet_07 illustre ce pattern précisément (le planner orchestre hotels/flights/activities), même si l'implémentation reste locale plutôt que via Bedrock Agents.

## Ancrage : predict-student-dropout

Le choix Flask+Gunicorn n'est jamais comparé aux alternatives dans le projet — un bon exercice 3.1 consiste à le faire a posteriori. Le trafic réel d'un outil de prédiction de décrochage scolaire (utilisé par un établissement, pas en continu à haute fréquence) ressemble probablement plus à un usage sporadique qu'à un besoin de latence sub-seconde permanent — ce qui plaiderait pour un endpoint **serverless** plutôt que temps réel une fois sur AWS, à l'inverse de ce que `BILAN-ENTREPRISE.md` a implicitement choisi (améliorer le serveur temps réel existant plutôt que remettre en question le mode de déploiement lui-même). Ce n'est pas une erreur du projet — c'est un rappel que 3.1 demande d'abord de connaître le profil de trafic AVANT de choisir l'infrastructure, une question jamais posée explicitement dans le projet local.

## Pièges classiques

- **Temps réel vs serverless vs asynchrone vs batch** : la question type d'examen décrit un profil de trafic (constant/sporadique/lourd-mais-tolérant-au-délai/gros-volume-différé) et demande de choisir — mémoriser le mapping profil→mode plutôt que les définitions seules.
- **Serverless a un cold start** : un piège classique consiste à proposer serverless pour un cas nécessitant une latence garantie et constante — serverless a un délai de démarrage (cold start) après une période d'inactivité, incompatible avec une exigence de latence stricte.
- **Agent vs simple FM avec RAG** : un agent (3.1.6) appelle des outils/API et enchaîne des décisions ; un système RAG classique (Domaine 1/2) récupère des documents puis génère une réponse en une seule passe. Si l'énoncé décrit plusieurs étapes séquentielles avec des appels d'outils, c'est un agent.
- **Custom Model Import vs fine-tuning natif Bedrock** : Custom Model Import sert à faire tourner un modèle entraîné EN DEHORS d'AWS (Hugging Face, etc.) sur l'infra Bedrock ; ce n'est pas la même chose que fine-tuner un FM Bedrock existant avec des données propriétaires (Domaine 2.2).
