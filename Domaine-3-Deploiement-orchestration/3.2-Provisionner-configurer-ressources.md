# 3.2 — Provisionner et configurer les ressources pour les charges ML/IA

Task statement officiel MLA-C02 : *Task 3.2: Provision and configure resources for ML and AI workloads based on existing architecture and requirements.* Onze skills (3.2.1 à 3.2.11) — le task statement avec le plus de skills de tout l'examen. Un point retiré depuis MLA-C01 (bring your own container avec SageMaker), cinq ajoutés, tous liés aux FM/agents/GPU : knowledge bases Bedrock (3.2.7), pipelines de retrieval (3.2.8), gestion d'état d'agent (3.2.9), scaling GPU (3.2.10), infrastructure de workflow agentique (3.2.11).

## En une phrase

Une fois le MODE de déploiement choisi (3.1), il faut dimensionner et configurer concrètement les ressources qui le font tourner — combien d'instances, quel type, dans quel réseau, avec quelle stratégie de scaling.

## Analogie

C'est le domaine le plus honnêtement absent du cahier. `Dockerfile` (predict-student-dropout) construit et configure un conteneur, mais rien n'y provisionne ou ne dimensionne une infrastructure — le conteneur tourne sur UNE machine, sans auto scaling, sans VPC dédié, sans notion de type d'instance à choisir. `docker-compose.yml` (Projet_08) va un peu plus loin en orchestrant plusieurs conteneurs ensemble (l'app + Postgres), le point de départ conceptuel le plus proche d'une vraie stack de provisioning, mais sans jamais toucher à de l'Infrastructure as Code (CloudFormation/CDK) ni à du GPU.

## Vocabulaire

| Terme AWS | Définition simple | Point de repère (cahier ou équivalent connu) |
|---|---|---|
| **On-demand vs provisioned/reserved** | On-demand : payer à l'usage, flexible, plus cher. Provisioned/Reserved : engagement à l'avance, moins cher, moins flexible | Aucun équivalent — aucun projet du cahier n'a jamais réfléchi à un modèle de tarification |
| **CloudFormation / AWS CDK** | Décrire l'infrastructure en code (JSON/YAML ou langage de programmation), reproductible et versionnable | Aucun équivalent — `docker-compose.yml` décrit des CONTENEURS en code, pas de l'infrastructure cloud (réseau, IAM, scaling) |
| **VPC (Virtual Private Cloud)** | Réseau privé isolé où tournent les ressources AWS | Aucun équivalent — tout tourne en local ou sur une seule machine dans le cahier, jamais de notion d'isolement réseau |
| **SageMaker AI SDK pour Python / Boto3** | Bibliothèques pour déployer/gérer des ressources SageMaker par le code plutôt qu'à la console | Le rôle que jouerait un script Python appelant `sagemaker.Session()` plutôt que cliquer dans la console AWS |
| **Auto scaling (métriques)** | Ajouter/retirer des instances automatiquement selon une métrique (CPU, nombre de requêtes, latence) | Aucun équivalent — Gunicorn tourne avec un nombre FIXE de workers (`--workers 2`), jamais ajusté dynamiquement |
| **Amazon Bedrock Knowledge Bases** | Service managé qui indexe des documents et gère le retrieval pour un système RAG, sans gérer soi-même la base vectorielle | Remplacerait toute la logique de recherche par similarité écrite à la main dans Projet_04/07/08 (`src/embeddings/`) |
| **GPU scaling** | Dimensionner et faire évoluer des ressources GPU spécifiquement (plus cher, plus rare, souvent le goulot d'étranglement) | Aucun équivalent — tous les entraînements du cahier (même Projet_05, deep learning) tournent en local, souvent sur CPU |
| **Agent state management** | Conserver le contexte/l'état d'un agent entre plusieurs étapes ou appels | Projet_07 gère un état implicitement (le planner garde le fil d'une réservation en cours) — jamais nommé ni traité comme une préoccupation d'infrastructure à part |

## Comment ça marche en détail

Le provisioning se décide sur trois axes indépendants. **Type d'achat** (3.2.1, 3.2.6 en Domaine 4) : on-demand par défaut, provisioned/reserved dès que la charge est prévisible et soutenue dans le temps — un arbitrage jamais nécessaire dans le cahier puisqu'aucun projet ne tourne en continu sur une infra facturée. **Infrastructure as Code** (3.2.2) : CloudFormation ou CDK décrivent l'infra (réseau, rôles IAM, endpoints) de façon reproductible, l'équivalent "cloud" de ce que `docker-compose.yml` fait pour des conteneurs locaux — la différence de fond est que `docker-compose` ne provisionne RIEN chez AWS, il orchestre seulement des conteneurs déjà sur une machine existante. **Réseau et sécurité** (3.2.4, VPC) : un endpoint SageMaker peut être configuré pour vivre entièrement dans un VPC privé, sans jamais transiter par l'internet public — une préoccupation totalement absente du cahier, où `app.py` écoute simplement sur `0.0.0.0` sans notion de périmètre réseau.

Pour les charges génératives/agentiques spécifiquement, le provisioning se complique : une Knowledge Base Bedrock (3.2.7) demande de configurer une base vectorielle sous-jacente (OpenSearch Service, souvent), des pipelines de retrieval à ajuster (3.2.8), et pour un système d'agents, une gestion d'état (3.2.9 — où et comment le contexte d'une conversation ou d'une tâche en cours est conservé entre deux appels) et une infrastructure dédiée au déploiement du workflow agentique lui-même (3.2.11). Le GPU (3.2.10) introduit une contrainte supplémentaire : c'est une ressource rare et chère, donc le scaling doit être pensé différemment d'un simple CPU (démarrage plus lent, coût par heure bien plus élevé, souvent un facteur limitant avant même le CPU/mémoire).

## Un exemple annoté

```yaml
# Projet_08, docker-compose.yml — le point de départ le plus proche d'un
# "provisioning" dans le cahier, mais uniquement local :
services:
  app:
    build: .
    depends_on: [db]
  db:
    image: postgres:16
    volumes: ["pgdata:/var/lib/postgresql/data"]
# Ce que ça NE fait PAS, et que 3.2 demande : pas de VPC, pas de choix de
# type d'instance, pas d'auto scaling, pas de rôle IAM dédié — tout tourne
# sur UNE machine, avec UNE configuration réseau (celle de Docker), figée.
# L'équivalent "cloud" en CloudFormation/CDK décrirait explicitement combien
# d'instances, de quel type, dans quel VPC/subnet, avec quelle policy IAM —
# reproductible et versionné, pas juste "ce qui tourne sur ma machine".
```

## Ancrage : predict-student-dropout

`Dockerfile` configure Gunicorn avec `--workers 2`, un nombre FIXE choisi arbitrairement (documenté comme "à ajuster selon la charge réelle" dans le commentaire du fichier) — c'est exactement l'absence du concept d'auto scaling (3.2.6, développé au Domaine 4.2) : sur AWS, ce nombre de workers fixe deviendrait une politique de scaling basée sur une métrique réelle (CPU, nombre de requêtes en attente), plutôt qu'une estimation figée au moment d'écrire le Dockerfile.

## Pièges classiques

- **On-demand vs provisioned/reserved** : un scénario qui décrit une charge STABLE et PRÉVISIBLE sur plusieurs mois pointe vers provisioned/reserved (moins cher) ; une charge IMPRÉVISIBLE ou ponctuelle pointe vers on-demand (flexible).
- **CloudFormation/CDK vs Boto3/SDK** : CloudFormation/CDK décrivent et provisionnent de l'INFRASTRUCTURE (VPC, rôles, endpoints) de façon déclarative ; le SDK SageMaker/Boto3 sert à des ACTIONS ponctuelles par le code (lancer un job, déployer un modèle) — les deux se combinent, l'un ne remplace pas l'autre.
- **VPC pour un endpoint SageMaker** : un scénario qui insiste sur "les données ne doivent jamais transiter par l'internet public" pointe vers un endpoint configuré dans un VPC privé (3.2.4), pas juste vers du chiffrement (Domaine 1.3/4.3 — chiffrer protège la donnée, l'isolement réseau protège le chemin qu'elle emprunte).
- **Bring your own container (BYOC), retiré de C02** : si une source d'étude mentionne encore BYOC comme skill à part entière, c'est un signal qu'elle date de MLA-C01 — ce point a été retiré du guide C02, à ne pas sur-pondérer en révision.

## Test de Feynman

- `docker-compose.yml` (Projet_08) orchestre deux conteneurs sur UNE machine. Pourquoi ce n'est PAS la même chose que provisionner de l'infrastructure AWS avec CloudFormation/CDK, même si les deux "décrivent l'infra en fichier" ?
- Gunicorn tourne avec `--workers 2`, un nombre fixe. Décris concrètement ce que ferait une politique d'auto scaling AWS à la place, et sur quelle métrique elle se baserait probablement pour ce service précis.
- Pourquoi une base de données vectorielle (Domaine 1.1.7) redevient-elle une question de PROVISIONING ici (3.2.7, Knowledge Bases Bedrock), alors qu'elle avait déjà été vue comme une question de STOCKAGE en Domaine 1 ?
- Le GPU scaling (3.2.10) est traité comme un cas à part du scaling classique. Pourquoi un modèle d'entraînement GPU ne peut-il pas simplement "ajouter plus d'instances" de la même façon qu'un service Flask CPU comme predict-student-dropout ?
- Projet_07 garde un état de réservation en cours à travers plusieurs étapes de son agent. Pourquoi cette gestion d'état deviendrait-elle un problème d'infrastructure (3.2.9) plutôt qu'un simple détail de code, une fois l'agent déployé sur plusieurs instances en parallèle ?
