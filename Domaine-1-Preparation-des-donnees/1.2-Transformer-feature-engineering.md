# 1.2 — Transformer les données et faire du feature engineering

Task statement officiel (guide MLA-C01, à recaler le 1er septembre si MLA-C02 change le libellé) : *Transform data and perform feature engineering.*

## En une phrase

Une fois la donnée stockée (1.1), il faut la nettoyer et la faire ressembler à ce qu'un modèle peut effectivement apprendre — et sur AWS, ce travail se fait avec des outils dédiés plutôt qu'à la main dans un notebook.

## Analogie

C'est le domaine le plus proche de ce que le cahier connaît déjà. Projet_02 (`build_training_table`, `fit_scaler`) fait exactement ce travail : nettoyage, standardisation, encodage — en pandas/scikit-learn, en local, sur un seul fichier. Projet_08 fait aussi de la transformation de données (parser 19 PDF en DataFrame avec des regex). La nouveauté AWS n'est pas le concept — c'est de faire la même chose à une échelle où pandas ne tient plus en mémoire sur une seule machine, avec des outils managés (Glue, DataBrew, Spark sur EMR) à la place d'un script Python local.

## Vocabulaire

| Terme AWS | Définition simple | Point de repère (cahier) |
|---|---|---|
| **AWS Glue** | Service ETL managé (Extract-Transform-Load), génère et exécute du PySpark sans gérer de cluster soi-même | Le grand frère industriel de `build_training_table` (Projet_02), mais distribué |
| **AWS Glue DataBrew** | Interface visuelle (sans code) pour nettoyer/transformer des données | Comme ouvrir un CSV dans un tableur avec des recettes de nettoyage réutilisables, plutôt que du code pandas |
| **Amazon EMR** | Cluster Spark/Hadoop managé, pour des transformations à très grande échelle avec du contrôle fin | Utile quand Glue ne suffit pas ou qu'on a déjà du code Spark existant |
| **SageMaker Data Wrangler** | Interface d'exploration/transformation intégrée à SageMaker, connectée à Feature Store | Le pont entre "nettoyer la donnée" et "l'utiliser pour entraîner" |
| **SageMaker Feature Store** | Stocke les features calculées une fois, réutilisables entre entraînement et inférence, avec versions | Corrige exactement le problème que `chercher_dans_la_base_de_connaissance` avait AVANT la mise en cache dans Projet_08 : ne pas recalculer ce qui ne change pas |
| **One-hot encoding / binary encoding / label encoding** | Techniques pour transformer une variable catégorielle en nombres | Vu dans Projet_02 (encodage des variables catégorielles avant `RandomForestClassifier`) |
| **Tokenization** | Découper du texte en unités (mots, sous-mots) exploitables par un modèle | Vu dans Projet_04/07/08 (recherche sémantique — les embeddings tokenisent avant d'encoder) |
| **Binning / normalization / log transformation** | Techniques de mise à l'échelle ou de regroupement d'une variable numérique | Proche de `fit_scaler` (Projet_02), en plus riche |
| **SageMaker Ground Truth** | Service de labellisation de données (humains + suggestions automatiques) | Pas d'équivalent — dans le cahier, toutes les données étaient déjà labellisées (`orders.status`, catégories des PDF) |
| **Amazon Mechanical Turk** | Marketplace de micro-tâches humaines, utilisable par Ground Truth pour labelliser à grande échelle | — |

## Comment ça marche en détail

Le choix d'outil dépend de deux critères : le volume de données, et qui doit faire le travail (un data engineer qui code, ou quelqu'un qui préfère une interface visuelle). Pour un volume qui tient sur une machine, un notebook SageMaker avec pandas suffit — exactement le mode de Projet_02. Dès que ça ne tient plus en mémoire, Glue (du code généré, exécuté sur un cluster Spark serverless) ou EMR (un vrai cluster, plus de contrôle, plus de gestion) prennent le relais. DataBrew se situe à part : conçu pour quelqu'un qui veut nettoyer des données sans écrire de code, avec des "recettes" de transformation réutilisables et un aperçu visuel immédiat de l'effet de chaque étape.

Le feature engineering proprement dit reste conceptuellement identique à ce que fait Projet_02, juste avec plus de vocabulaire précis à l'examen : le *scaling* (mettre toutes les variables numériques sur une échelle comparable, ce que fait `StandardScaler` dans Projet_02), le *binning* (regrouper une variable continue en catégories, par exemple des tranches d'âge), la *log transformation* (compresser une distribution très étalée, comme des revenus), et l'encodage catégoriel (one-hot pour peu de catégories, binary encoding quand il y en a beaucoup, ce qui évite l'explosion du nombre de colonnes que produirait le one-hot).

La vraie nouveauté conceptuelle du domaine, c'est le **Feature Store** : dans Projet_02, la feature engineering est recalculée à chaque exécution du script, parce qu'il n'y a qu'un seul consommateur (l'entraînement). En production, la même feature ("montant total des commandes d'un client sur 90 jours") doit être calculée de façon identique à l'entraînement ET à l'inférence — un écart entre les deux (le "training-serving skew") dégrade silencieusement la qualité du modèle. Feature Store centralise le calcul et la définition de chaque feature pour que les deux usages y accèdent de façon cohérente, exactement l'esprit de `encoder_la_base_de_connaissance` dans Projet_08 (calculer une fois, réutiliser partout) mais appliqué aux features d'un modèle plutôt qu'à des embeddings de documents.

Porter ce fichier vers AWS reviendrait à transformer chaque méthode de `DataPreparation` en une étape d'un job Glue (ou d'un flow SageMaker Data Wrangler pour la version sans code) : le fichier entier devient une recette réutilisable et versionnée, plutôt qu'un script relancé à la main à chaque fois.

## Pièges classiques

- **Glue vs DataBrew vs EMR** : DataBrew = sans code, interface visuelle, cas d'usage simples et exploratoires. Glue = ETL managé avec du code (généré ou écrit), le choix par défaut pour un pipeline de production. EMR = quand on a besoin de contrôle total sur le cluster Spark/Hadoop, ou du code Spark déjà existant à réutiliser tel quel.
- **One-hot vs binary vs label encoding** : one-hot explose en nombre de colonnes si la variable a beaucoup de catégories (attention aux questions qui donnent un nombre de catégories élevé — c'est un indice vers binary encoding). Label encoding introduit un ordre numérique arbitraire, dangereux pour un algorithme qui interpréterait cet ordre comme une vraie relation (à éviter sauf variable réellement ordinale).
- **Feature Store vs juste recalculer** : la question type décrit un scénario où le score du modèle en production diverge de ses performances en test — souvent un signe de training-serving skew, réponse attendue : centraliser via Feature Store, pas "réentraîner le modèle".
- **Ground Truth vs Mechanical Turk** : Ground Truth est le service qui orchestre le labelling (workflow, humains internes ou externes, suggestions automatiques) ; Mechanical Turk est une des sources de main-d'œuvre humaine que Ground Truth peut utiliser, pas un concurrent de Ground Truth.
