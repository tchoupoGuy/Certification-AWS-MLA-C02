# 1.1 — Collecter et stocker les données

Task statement officiel MLA-C02 (guide publié le 1er septembre, confirmé) : *Task 1.1: Collect and store data.* Neuf skills officiels (1.1.1 à 1.1.9) ; les six premiers sont ceux déjà couverts ci-dessous (inchangés depuis MLA-C01), les trois derniers sont détaillés dans "Nouveauté MLA-C02".

## En une phrase

Avant de faire quoi que ce soit avec des données sur AWS, il faut choisir où elles vivent (objet, fichier, bloc, base relationnelle, flux) et comment elles y arrivent — et ce choix dépend entièrement de qui va les lire ensuite et comment.

## Analogie

Dans le cahier, cette question ne s'est jamais posée : Projet_01 et Projet_08 stockent tout dans PostgreSQL, un seul type de stockage, choisi une fois pour toutes. Ce domaine AWS, c'est l'inverse : il y a désormais 5-6 façons de stocker la même donnée (S3, EFS, FSx, EBS, RDS, DynamoDB) et le bon choix change selon le cas d'usage — plus proche du choix "SQLite vs PostgreSQL" fait consciemment au fil des projets du cahier, mais avec beaucoup plus d'options et un axe supplémentaire complètement absent jusqu'ici : l'ingestion en flux continu (streaming), puisque toutes les données du cahier étaient déjà "au repos" (un CSV, une base, des PDF) avant d'être traitées.

## Vocabulaire

| Terme AWS | Définition simple | Point de repère (cahier ou équivalent connu) |
|---|---|---|
| **Amazon S3** | Stockage objet : des fichiers dans des "buckets", pas de hiérarchie réelle, capacité quasi illimitée | Le plus proche de "un gros dossier de fichiers", mais accessible par HTTP depuis n'importe quel service AWS |
| **Amazon EBS** | Disque dur virtuel attaché à UNE seule instance EC2 à la fois | Le disque local d'un ordinateur — pas partageable |
| **Amazon EFS** | Système de fichiers partagé (NFS), monté par plusieurs instances/conteneurs en même temps | Un dossier réseau partagé — utile quand plusieurs machines d'entraînement doivent lire les mêmes fichiers |
| **Amazon FSx for NetApp ONTAP** | Système de fichiers managé compatible NetApp, avec snapshots et fonctions avancées | Pertinent surtout en migration depuis une infra NetApp on-premise |
| **Amazon RDS** | Base de données relationnelle managée (Postgres, MySQL...) | Exactement ce que fait `docker-compose` + Postgres dans Projet_08, mais géré par AWS |
| **Amazon DynamoDB** | Base NoSQL clé-valeur/document, managée, scaling automatique | Pas d'équivalent dans le cahier — proche d'un gros dictionnaire distribué |
| **Amazon Kinesis Data Streams** | Ingestion de données en flux continu, consommateurs personnalisés | Rien de comparable dans le cahier — toutes les données y étaient déjà arrêtées |
| **Amazon Kinesis Data Firehose** | Comme Kinesis Data Streams, mais livraison automatique vers S3/Redshift/OpenSearch, sans code consommateur | Un tuyau managé plutôt qu'un flux qu'on doit lire soi-même |
| **Apache Kafka / Amazon MSK** | Kafka managé par AWS, pour qui a déjà un écosystème Kafka | — |
| **Parquet / ORC** | Formats **colonnaires** : compressés, rapides à lire quand on ne veut que quelques colonnes sur beaucoup de lignes | — |
| **CSV / JSON** | Formats **ligne par ligne**, lisibles par un humain, mais lents à grande échelle | Format utilisé partout dans le cahier (`seed.sql`, exports CSV) |
| **RecordIO** | Format binaire utilisé par les algorithmes intégrés SageMaker en "pipe mode" | — |
| **SageMaker Data Wrangler** | Interface visuelle pour ingérer/transformer des données avant l'entraînement | — |
| **SageMaker Feature Store** | Entrepôt centralisé de features, réutilisables entre entraînement et inférence | Résout un problème que Projet_02 n'a jamais eu à affronter : Projet_02 recalcule ses features à chaque fois, dans le même script |

## Comment ça marche en détail

Le choix de stockage se fait sur deux axes indépendants. Premier axe, la **forme d'accès** : bloc (EBS — un seul consommateur, très rapide, pas partageable), fichier (EFS/FSx — plusieurs consommateurs, hiérarchie de dossiers classique), objet (S3 — le plus scalable, accessible en HTTP, pas de vraie hiérarchie), ou base de données (RDS pour du relationnel avec contraintes et jointures, DynamoDB pour du clé-valeur qui doit encaisser un débit élevé sans schéma fixe). Pour l'entraînement ML sur SageMaker, S3 est le choix par défaut à 90 % des cas — c'est ce que les algorithmes intégrés et les jobs d'entraînement attendent nativement.

Second axe, la **vitesse d'arrivée** : donnée déjà là (un fichier existant qu'on charge une fois — c'est tout ce que le cahier a fait jusqu'ici) contre donnée en flux continu (des événements qui arrivent en permanence — des logs, des clics, des transactions). Pour le flux continu, Kinesis Data Streams s'utilise quand on veut écrire son propre code consommateur avec un contrôle fin (comme un abonnement à une file), alors que Kinesis Data Firehose s'utilise quand on veut juste que les données atterrissent quelque part (S3, Redshift) sans écrire de consommateur — Firehose fait le buffering et la livraison tout seul. Apache Flink (via Amazon Managed Service for Apache Flink) sert à transformer un flux en vol, entre l'ingestion et le stockage final.

Le format de fichier compte autant que le support de stockage. CSV et JSON sont lisibles par un humain mais lents à grande échelle car il faut lire la ligne entière même si on ne veut qu'une colonne. Parquet et ORC stockent par colonne : lire uniquement les colonnes utiles est bien plus rapide, et la compression est meilleure car les valeurs d'une même colonne se ressemblent. RecordIO est spécifique à SageMaker : les algorithmes intégrés peuvent lire ce format en "pipe mode", c'est-à-dire en streaming direct depuis S3 sans copier tout le jeu de données sur le disque local avant de démarrer — ça réduit le temps de démarrage et l'espace disque nécessaire.

## Un exemple annoté

```bash
# Charger un CSV existant dans un bucket S3 (équivalent "ingestion" le plus simple)
aws s3 cp donnees_clients.csv s3://mon-bucket-ml/bruts/donnees_clients.csv

# Convertir en Parquet avec AWS Glue (job PySpark managé) plutôt qu'à la main :
# un job Glue lit le CSV depuis S3, écrit du Parquet partitionné en sortie —
# le choix de Parquet ici n'est pas cosmétique : SageMaker Data Wrangler et les
# jobs d'entraînement suivants liront BEAUCOUP plus vite un Parquet partitionné
# qu'un gros CSV plat.
```

Le point à retenir de cet exemple : l'ingestion n'est presque jamais "un seul geste". C'est une chaîne — S3 pour le stockage brut, Glue pour la transformation de format, puis S3 de nouveau (ou Feature Store) pour la donnée prête à l'entraînement.

C'est en soi un bon exercice : la réponse "il faut toujours du Parquet" est un piège, la bonne réponse dépend du volume. Deuxième question à se poser : ce dataset (les "Curricular units 1st/2nd sem (grade)" par exemple) est un instantané figé, jamais mis à jour en continu — Kinesis serait donc une sur-ingénierie totale ici, contrairement à un flux réel d'inscriptions d'étudiants qui arriverait en continu.

## Pièges classiques

- **EBS vs EFS vs FSx vs S3** : la question type oppose ces quatre services sur un scénario ("plusieurs instances d'entraînement distribué doivent lire les mêmes fichiers simultanément" → EFS, pas EBS qui n'est attachable qu'à une seule instance). S3 reste le choix par défaut sauf besoin POSIX explicite (EFS) ou migration NetApp (FSx for ONTAP).
- **Kinesis Data Streams vs Firehose** : si l'énoncé mentionne "sans gérer de code consommateur" ou "livraison automatique vers S3", c'est Firehose. Si l'énoncé mentionne un traitement personnalisé en temps quasi réel avec plusieurs consommateurs indépendants, c'est Data Streams.
- **RDS vs DynamoDB** : schéma fixe + jointures + transactions ACID complexes → RDS. Débit élevé, schéma flexible, latence à un chiffre de milliseconde à grande échelle → DynamoDB. Projet_08 a fait ce choix implicitement (RDS/Postgres) sans jamais comparer à DynamoDB — bon réflexe à construire.
- **Format colonnaire vs format ligne** : dès que l'énoncé parle d'"optimiser le coût de lecture" ou de "grand volume, peu de colonnes utilisées", la réponse est Parquet/ORC, jamais CSV/JSON.
