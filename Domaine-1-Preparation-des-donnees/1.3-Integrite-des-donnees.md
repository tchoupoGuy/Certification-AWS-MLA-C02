# 1.3 — Garantir l'intégrité des données et préparer la modélisation

Task statement officiel (guide MLA-C01, à recaler le 1er septembre si MLA-C02 change le libellé) : *Ensure data integrity and prepare data for modeling.*

## En une phrase

Avant d'entraîner quoi que ce soit, il faut vérifier que la donnée est correcte (intégrité) et qu'elle ne va pas apprendre au modèle à discriminer injustement (biais) — deux problèmes différents, souvent confondus.

## Analogie

Projet_08 a déjà touché à la moitié "intégrité" de ce domaine, sans le vocabulaire AWS : les totaux de commandes incohérents dans `seed.sql` (9998 au lieu de 9996) sont exactement le genre de défaut qu'AWS Glue Data Quality ou DataBrew sont censés détecter automatiquement, plutôt qu'à la main via une vérification arithmétique ponctuelle. La moitié "biais" (class imbalance, biais de sélection, PII/PHI) n'a en revanche aucun équivalent dans le cahier — aucun projet n'a mesuré si une variable protégée (âge, genre, origine) influençait injustement une prédiction, ni chiffré/anonymisé de données personnelles.

## Comment ça marche en détail

Ce domaine sépare deux préoccupations qu'il vaut la peine de garder distinctes. **L'intégrité** répond à "cette donnée est-elle correcte ?" : pas de valeurs manquantes inattendues, pas de doublons, les totaux qui correspondent bien à la somme de leurs parties (exactement le bug de Projet_08). AWS Glue Data Quality et DataBrew automatisent ce contrôle avec des règles déclaratives, plutôt que des vérifications ad hoc écrites à la main.

**Le biais** répond à une question différente : "même si la donnée est correcte, favorise-t-elle injustement un groupe ?". SageMaker Clarify mesure ça à deux moments : avant l'entraînement (biais présent dans les données elles-mêmes — par exemple, la classe positive est-elle très sous-représentée dans un sous-groupe démographique) et après l'entraînement (le modèle amplifie-t-il ce biais dans ses prédictions). Le class imbalance est le cas le plus simple à comprendre : si 95 % des exemples d'entraînement appartiennent à une classe, le modèle peut atteindre 95 % d'exactitude en prédisant toujours cette classe — un score qui semble bon mais qui ne veut rien dire. Les stratégies de correction (resampling, génération de données synthétiques) rééquilibrent artificiellement les classes avant l'entraînement.

Le troisième axe est la conformité : classifier la donnée (savoir où sont les PII/PHI), l'anonymiser ou la masquer quand c'est possible, la chiffrer quand ce n'est pas possible, et respecter les contraintes de résidence (une donnée européenne qui doit rester dans une région AWS européenne, par exemple). Enfin, une fois la donnée validée et débiaisée, la préparer pour l'entraînement veut dire : la découper en train/test/validation (data splitting), la mélanger (shuffling — éviter qu'un modèle apprenne un ordre qui n'a pas de sens), l'augmenter si besoin (data augmentation), et la rendre disponible au job d'entraînement via EFS ou FSx (le lien avec 1.1 : le stockage final dépend de comment le job d'entraînement va la lire).

## Ancrage : predict-student-dropout

**Correction avant tout** : la première version de cette section décrivait un bug (SMOTE appliqué avant le split train/test) trouvé dans `training/PreValModels/data_validation.py`. En vérifiant pour le corriger, ce fichier s'est avéré être une ancienne version, autonome (`if __name__ == "__main__":`), qui n'est plus utilisée par le pipeline réel. Le vrai pipeline vit dans `training/PreValModels/infrastructure/` (architecture hexagonale : `domain/interfaces/` définit des ports, `infrastructure/` fournit les adaptateurs), orchestré par `main.py` + `application/use_cases/training_pipeline.py`. Ce fichier ancien mérite d'être discuté avec toi pour savoir s'il faut l'archiver — mais le bug lui-même n'existe pas dans le code qui tourne réellement.

Et la bonne nouvelle, c'est que la vraie version est un MEILLEUR exemple pédagogique que le bug que je pensais avoir trouvé. `infrastructure/data_validation.py` sépare d'abord, avec stratification :

```python
def split_and_balance_data(self, test_size=0.2, random_state=23):
    self.X_train, self.X_test, self.y_train, self.y_test = train_test_split(
        self.X, self.y, test_size=test_size, random_state=random_state, stratify=self.y,
    )
    return self.X_train, self.X_test, self.y_train, self.y_test
```

Puis `infrastructure/model_selection.py` va plus loin que "SMOTE seulement sur le train" : il place SMOTE À L'INTÉRIEUR d'un pipeline `imblearn`, avec le modèle, exécuté par la recherche d'hyperparamètres (`HalvingRandomSearchCV`) :

```python
def _build_pipeline(self, model):
    steps = []
    if self.use_smote:
        steps.append(("smote", SMOTE(random_state=self.random_state)))
    steps.append(("model", model))
    return Pipeline(steps=steps)
```

Pourquoi c'est plus rigoureux qu'un simple "split puis SMOTE une fois" : la validation croisée (`StratifiedKFold`) découpe le train en plusieurs plis à chaque itération de la recherche d'hyperparamètres. Si SMOTE était appliqué une seule fois avant la CV, les exemples synthétiques d'un pli pourraient être générés à partir de voisins qui se retrouvent dans un AUTRE pli utilisé pour la validation — une fuite plus subtile que la fuite train/test, mais de la même famille. En mettant SMOTE dans le pipeline, il est recalculé À CHAQUE pli, uniquement sur les données d'entraînement de ce pli précis. Le code va même jusqu'à sécuriser ce mécanisme (`_compute_min_safe_resources`) pour garantir qu'aucun pli ne devienne trop petit pour que SMOTE fonctionne.

Même rigueur côté nettoyage : `infrastructure/data_preparation.py` sépare explicitement "apprendre" et "appliquer" — `handle_outliers`/`feature_selection` apprennent leurs bornes/colonnes sur le train et les mémorisent, tandis que `apply_outlier_bounds`/`apply_feature_selection` réappliquent ces décisions au test sans jamais les recalculer dessus (le commentaire du code est explicite : *"jamais recalculées sur le test, pour ne pas fuiter d'information dessus"*).

Le schéma TFDV (`generate_schema`/`validate_schema`) reste l'équivalent exact d'AWS Glue Data Quality (ou du baseline de SageMaker Model Monitor, vu plus loin en Domaine 4) : des statistiques calculées sur le train, un schéma déduit, puis le test comparé à ce schéma pour détecter des anomalies.

## Pièges classiques

- **Intégrité vs biais** : l'examen aime poser un scénario où une donnée est parfaitement correcte (aucune valeur manquante, aucun doublon) mais quand même problématique (un groupe démographique sous-représenté). La réponse attendue est une métrique de biais (Clarify, DPL), pas une vérification de qualité (Glue Data Quality) — ce sont deux outils différents pour deux problèmes différents.
- **Class imbalance vs accuracy trompeuse** : si un énoncé donne une exactitude très élevée mais une classe très minoritaire, c'est un signal d'alerte, pas une bonne nouvelle — la réponse attendue implique souvent le rappel (recall) sur la classe minoritaire, ou une stratégie de rééquilibrage, jamais "le modèle est prêt pour la production".
- **Anonymisation vs chiffrement** : anonymiser retire l'information identifiante de façon irréversible (utile quand on n'a plus besoin de revenir à l'identité) ; chiffrer la rend illisible mais réversible avec la bonne clé (utile quand on doit pouvoir la déchiffrer plus tard). Confondre les deux dans une réponse d'examen est une erreur fréquente.
- **SageMaker Clarify avant vs après l'entraînement** : "pre-training bias" mesure le déséquilibre dans les données elles-mêmes ; "post-training bias" mesure si le modèle entraîné a amplifié ou introduit un déséquilibre dans ses prédictions — un scénario d'examen qui parle de "avant même d'entraîner" pointe vers les métriques pre-training (CI, DPL).
