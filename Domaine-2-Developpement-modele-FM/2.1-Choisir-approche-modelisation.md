# 2.1 — Choisir une approche de modélisation pour une solution ML/IA

Task statement officiel MLA-C02 : *Task 2.1: Choose appropriate modeling approaches for ML and AI solutions.* Huit skills (2.1.1 à 2.1.8) — le task statement le plus directement transformé par le virage gen-AI : sur MLA-C01, "choisir une approche" voulait dire choisir entre quelques algorithmes ML classiques ; sur MLA-C02, ça veut dire choisir entre ML classique, modèle de fondation prêt à l'emploi, fine-tuning, ou service IA managé — quatre familles de solutions, pas une.

## En une phrase

Avant d'écrire une seule ligne d'entraînement, il faut choisir la bonne famille de solution (ML classique entraîné from scratch, FM via Bedrock, service IA managé comme Rekognition/Comprehend) — et cette décision se prend sur des critères business (coût, latence, interprétabilité), pas sur la mode technique du moment.

## Analogie

Le cahier a déjà fait ce choix plusieurs fois, sans jamais le nommer explicitement comme une décision à comparer. Projet_02 entraîne un modèle from scratch (RandomForest) parce que le problème est structuré et le dataset petit. Projet_04/07/08 utilisent un LLM existant (via RAG) plutôt que d'en entraîner un — l'option "fine-tuner un modèle de fondation" n'a même jamais été essayée dans le cahier, alors que c'est un skill à part entière du domaine (2.1.2). predict-student-dropout a poussé la comparaison le plus loin : `model_selection.py` compare explicitement 3 algorithmes (Decision Tree, Random Forest, Gradient Boosting) sur les mêmes données, avec les mêmes métriques — la version la plus proche de ce que ce task statement demande, mais seulement à l'intérieur de la famille "ML classique", jamais face à un FM.

## Vocabulaire

| Terme AWS | Définition simple | Point de repère (cahier ou équivalent connu) |
|---|---|---|
| **Amazon Bedrock** | Accès managé à plusieurs FM (Anthropic, Amazon Nova, Meta, Mistral...) via une API unique, sans gérer d'infrastructure | Pas d'équivalent direct — Projet_04/07/08 utilisent des modèles locaux (`sentence-transformers`), pas un FM managé propriétaire |
| **SageMaker JumpStart** | Catalogue de modèles pré-entraînés (FM et ML classiques) déployables en un clic, avec fine-tuning intégré | Le pont entre "entraîner from scratch" (Projet_02) et "utiliser un FM tel quel" (Projet_04) |
| **Fine-tuning** | Ré-entraîner partiellement un modèle pré-entraîné sur des données spécifiques à un domaine | Jamais fait dans le cahier ni dans predict-student-dropout — tout y est entraîné from scratch ou utilisé sans adaptation |
| **RAG (Retrieval Augmented Generation)** | Injecter des documents pertinents dans le prompt d'un FM au moment de la requête, plutôt que de ré-entraîner le modèle | Exactement ce que font Projet_04/07/08 — c'est l'ancrage le plus solide de ce domaine |
| **AWS AI services** (Textract, Rekognition, Comprehend, Transcribe) | Services IA pré-construits pour une tâche précise (OCR, vision, NLP, transcription), zéro entraînement à faire | Aucun équivalent — Projet_05 (vision) et Projet_07/08 (extraction de texte de PDF) refont "à la main" ce que Textract/Rekognition feraient en un appel d'API |
| **Interprétabilité** | Capacité à expliquer pourquoi un modèle a produit telle prédiction | Un Decision Tree (predict-student-dropout, `model_selection.py`) est plus interprétable qu'un Gradient Boosting — le compromis est déjà visible dans le code, jamais discuté comme critère de choix |

## Comment ça marche en détail

Le choix se structure autour de quatre familles, du plus sur-mesure au plus prêt-à-l'emploi. **ML classique entraîné from scratch** (SageMaker built-in algorithms, script mode) : le bon choix quand le problème est structuré, les données tabulaires, le volume raisonnable, et l'interprétabilité importante — exactement le cas de predict-student-dropout. **FM via Bedrock, utilisé tel quel ou en RAG** : pertinent pour du texte/image non structuré, quand le "raisonnement" général d'un LLM suffit sans connaissance métier ultra-spécifique — le cas de Projet_04/07/08. **FM fine-tuné** : quand le FM générique ne suffit pas mais que ré-entraîner from scratch serait disproportionné (coût, données insuffisantes) — jamais illustré dans le cahier. **Service IA managé** : quand la tâche est un besoin générique déjà résolu par AWS (extraire du texte d'un PDF, détecter des visages) — Projet_07/08 auraient pu utiliser Textract au lieu de parser les PDF à la main.

Les critères de décision (2.1.4, 2.1.6, 2.1.7) sont toujours un compromis à trois : **performance** (le modèle résout-il bien le problème), **coût** (entraîner from scratch coûte du temps de calcul ; un FM managé coûte à chaque appel, au token), **latence** (un Decision Tree répond en microsecondes ; un FM peut prendre plusieurs secondes). predict-student-dropout illustre concrètement ce compromis dans son propre choix : Decision Tree, Random Forest et Gradient Boosting sont comparés sur le même F1 pondéré, avec Gradient Boosting généralement le plus précis mais aussi le plus lent à entraîner et le moins interprétable — un arbitrage explicite entre performance et les deux autres axes.

## Un exemple annoté

```python
# predict-student-dropout : comparaison explicite de 3 approches "ML classique"
# (model_selection.py, build_default_models) — exactement l'esprit de 2.1.3
models = [
    {"model": DecisionTreeClassifier(), "name": "Decision Tree"},   # + interprétable, + rapide
    {"model": RandomForestClassifier(), "name": "Random Forest"},   # compromis
    {"model": GradientBoostingClassifier(), "name": "Gradient Boosting"},  # + précis, - interprétable
]
# Ce que le projet NE compare PAS (et que 2.1 demande d'envisager) :
# un FM via Bedrock pourrait-il résoudre ce problème de classification tabulaire ?
# Réponse attendue à l'examen : non — un FM est optimisé pour du texte/langage,
# pas pour une prédiction structurée sur 26 colonnes numériques/catégorielles.
# C'est le bon réflexe 2.1.3 : reconnaître qu'un FM n'est PAS toujours la
# meilleure réponse, malgré la tentation d'en faire l'option par défaut.
```

## Ancrage : predict-student-dropout

`training/PreValModels/application/config/training_config.py::build_default_models` définit les 3 candidats comparés. Le choix "ML classique" plutôt que FM n'est jamais justifié explicitement dans le code — un bon exercice de audit consiste à écrire cette justification a posteriori : le problème (prédire `Target` à partir de 26 variables tabulaires) n'a ni texte ni image en entrée, un FM n'apporterait rien qu'un modèle structuré ne fasse déjà, et coûterait largement plus cher par prédiction qu'un arbre de décision entraîné une fois. C'est un exemple concret de 2.1.4 (arbitrer entre solution sur-mesure et FM) où la réponse "FM" serait un piège classique d'examen : la présence de texte dans l'énoncé ne suffit pas, il faut que le FM apporte un avantage réel sur la tâche précise.

## Pièges classiques

- **RAG vs fine-tuning** : l'examen oppose souvent les deux sur un scénario "le modèle doit répondre avec des informations à jour/spécifiques à l'entreprise". RAG gagne quand l'information change souvent (pas besoin de ré-entraîner) ; le fine-tuning gagne quand c'est le *style*/*format* de réponse qui doit changer durablement, pas juste le contenu factuel.
- **FM vs ML classique sur données structurées** : un scénario qui décrit un problème tabulaire classique (churn, fraude, scoring) avec une tentation d'y appliquer un FM par réflexe — la bonne réponse reste souvent un modèle ML classique (SageMaker built-in algorithm), plus rapide, moins cher, plus interprétable.
- **AWS AI service vs SageMaker vs Bedrock** : si la tâche est générique et déjà résolue (OCR, transcription, détection de sentiment basique) → AI service (Textract, Comprehend). Si la tâche est propre à l'entreprise mais reste tabulaire/structurée → SageMaker. Si la tâche nécessite du langage naturel généraliste ou génératif → Bedrock.
