# 2.2 — Entraîner, affiner et personnaliser des modèles ML/IA

Task statement officiel MLA-C02 : *Task 2.2: Train, fine-tune, and customize models for ML and AI solutions.* Neuf skills (2.2.1 à 2.2.9). Par rapport à MLA-C01, deux points ont été retirés (utiliser des datasets personnalisés pour fine-tuner un modèle pré-entraîné ; réduire la taille d'un modèle par pruning/compression) et deux ajoutés (2.2.8 personnalisation par prompt engineering/fine-tuning, 2.2.9 optimisation des composants de retrieval/embedding) — le centre de gravité se déplace de "optimiser un modèle qu'on entraîne" vers "adapter un modèle qui existe déjà".

## En une phrase

Une fois l'approche choisie (2.1), il faut effectivement entraîner ou adapter le modèle — et sur AWS, ça veut dire déléguer le calcul à SageMaker plutôt que de faire tourner `.fit()` sur sa propre machine.

## Analogie

`model_selection.py` de predict-student-dropout est l'anchor le plus riche du cahier pour ce domaine : recherche d'hyperparamètres (`HalvingRandomSearchCV`), réduction du temps d'entraînement par élimination successive des mauvais candidats, ajustement d'hyperparamètres fondamentaux (profondeur d'arbre, nombre d'estimateurs). Tout ça tourne en local avec scikit-learn ; sur AWS, la même logique tourne dans un SageMaker Training Job, à plus grande échelle et sans gérer la machine soi-même. Le manque total du cahier : la personnalisation d'un FM (prompt engineering systématique, fine-tuning) — Projet_04/07/08 utilisent des prompts one-shot écrits à la main, jamais optimisés ou versionnés comme un vrai skill 2.2.8 le demanderait.

## Vocabulaire

| Terme AWS | Définition simple | Point de repère (cahier) |
|---|---|---|
| **SageMaker built-in algorithms** | Algorithmes ML prêts à l'emploi (XGBoost, Linear Learner...), optimisés pour tourner distribués sur SageMaker | Plus rapide à mettre en œuvre que `HalvingRandomSearchCV` en local, mais moins de contrôle fin |
| **Script mode** | Fournir son propre script d'entraînement (scikit-learn, PyTorch, TensorFlow) à SageMaker, qui gère l'infrastructure autour | L'équivalent direct de `model_selection.py` — même code, exécuté sur l'infra managée de SageMaker plutôt qu'en local |
| **SageMaker Automatic Model Tuning (AMT)** | Recherche d'hyperparamètres managée (bayésienne, aléatoire, grid) | L'équivalent AWS de `HalvingRandomSearchCV` — même objectif (trouver les meilleurs hyperparamètres), orchestré par SageMaker plutôt qu'en local |
| **Early stopping** | Arrêter l'entraînement dès que la performance sur validation cesse de s'améliorer | Le principe derrière le successive halving de `HalvingRandomSearchCV` (éliminer tôt les candidats faibles) |
| **Distributed training** | Répartir l'entraînement sur plusieurs machines/GPU en parallèle | Jamais nécessaire dans le cahier (datasets petits) — devient indispensable pour un FM ou un gros volume |
| **Overfitting / underfitting / catastrophic forgetting** | Trop coller aux données d'entraînement / pas assez apprendre / un FM fine-tuné qui "oublie" ses capacités générales en apprenant la tâche spécifique | Overfitting/underfitting vus en Projet_02/06 (comparaison train/test) ; catastrophic forgetting n'a pas d'équivalent — spécifique au fine-tuning de FM |
| **Ensembling** | Combiner plusieurs modèles pour améliorer la performance ou réduire le coût | Random Forest et Gradient Boosting (predict-student-dropout) SONT déjà des ensembles (d'arbres) — le principe est déjà là, sans être nommé comme tel au niveau "combiner plusieurs modèles entraînés séparément" |
| **Prompt engineering** | Concevoir soigneusement le prompt envoyé à un FM pour orienter sa réponse | Les prompts de Projet_04/07/08 sont écrits une fois, jamais itérés ou testés systématiquement comme le demande 2.2.8 |

## Comment ça marche en détail

Le point de départ, c'est le choix d'implémentation : **built-in algorithm** (zéro code d'entraînement à écrire, mais moins de flexibilité) contre **script mode** (on garde son propre code Python/scikit-learn/PyTorch, SageMaker fournit juste l'infra). predict-student-dropout, porté vers AWS, resterait en script mode : `model_selection.py` est déjà un script d'entraînement complet, il suffirait de l'envelopper dans le format attendu par un SageMaker Estimator plutôt que de le réécrire avec un built-in algorithm.

L'optimisation des hyperparamètres suit la même logique des deux côtés : SageMaker AMT explore l'espace des hyperparamètres (comme `HalvingRandomSearchCV` le fait déjà) mais peut paralléliser les essais sur plusieurs instances simultanément, ce que le local ne permet pas. Les techniques de réduction du temps d'entraînement (early stopping, distributed training) répondent au même problème que le successive halving de `HalvingRandomSearchCV` : arrêter d'investir du calcul sur des candidats qui ne s'amélioreront pas.

La vraie différence conceptuelle du domaine, c'est la personnalisation de FM (2.2.8, 2.2.9) : là où Projet_02/predict-student-dropout ajustent des hyperparamètres d'un modèle entraîné from scratch, personnaliser un FM veut dire soit affiner le prompt (sans toucher aux poids du modèle), soit fine-tuner (ajuster une petite partie des poids sur des données spécifiques), soit optimiser les composants de retrieval d'un système RAG (2.2.9 — améliorer la pertinence des documents récupérés avant de les injecter dans le prompt, ce que Projet_04/07/08 font implicitement via leur choix de modèle d'embedding, sans jamais le traiter comme un axe d'optimisation à part entière).

## Un exemple annoté

```python
# predict-student-dropout, model_selection.py — équivalent conceptuel d'un
# SageMaker Training Job en script mode + Automatic Model Tuning :
search = HalvingRandomSearchCV(
    pipeline,                          # préprocessing + modèle, comme un script SageMaker
    search_space,                      # équivalent du HyperparameterTuner de SageMaker AMT
    cv=StratifiedKFold(n_splits=self.cv_splits, shuffle=True),
    factor=3,                          # élimination successive = "early stopping" à l'échelle du tuning
    min_resources=self._min_resources, # sécurité anti-fuite (voir Domaine 1.3), pas d'équivalent SageMaker direct
)
# Porté vers AWS : ce même pipeline devient le script d'entraînement fourni à
# un SageMaker Estimator (script mode), et search_space devient l'espace de
# recherche configuré dans un HyperparameterTuner (AMT) — la logique métier
# (le pipeline imblearn, le choix de scoring f1_weighted) ne change pas,
# seule l'infrastructure d'exécution est déléguée à SageMaker.
```

## Ancrage : predict-student-dropout

`_compute_min_safe_resources` (dans `ModelSelection`) est un détail que peu de tutoriels SageMaker mentionnent mais qui illustre bien 2.2.5 (prévenir des problèmes d'entraînement) : il calcule la taille minimale de sous-échantillon nécessaire pour que SMOTE et la validation croisée fonctionnent correctement ensemble, évitant un plantage plutôt qu'un simple ajustement de performance. C'est le genre de garde-fou qu'un SageMaker Training Job avec un mauvais dimensionnement de `min_resources` dans AMT pourrait reproduire — un rappel que porter du code vers AWS ne supprime pas le besoin de comprendre ce que fait le code, seulement où il s'exécute.

## Pièges classiques

- **Built-in algorithm vs script mode** : si l'énoncé mentionne un algorithme standard sans besoin de logique métier particulière → built-in. Si l'énoncé mentionne du code existant (scikit-learn, PyTorch) ou une logique métier spécifique (comme le pipeline SMOTE de predict-student-dropout) → script mode.
- **AMT vs early stopping** : AMT cherche les MEILLEURS hyperparamètres (une recherche) ; early stopping arrête un entraînement individuel qui ne s'améliore plus (une décision au sein d'un seul entraînement). Les deux se combinent, ils ne s'opposent pas.
- **Fine-tuning vs prompt engineering** : un scénario qui décrit un besoin de changement de CONTENU factuel pointe vers RAG (voir 2.1) ; un besoin de changement de FORMAT/STYLE de réponse récurrent pointe vers le fine-tuning ; un ajustement ponctuel et peu coûteux pointe vers le prompt engineering seul.
- **Catastrophic forgetting** : une question qui décrit un FM fine-tuné qui a soudainement perdu des capacités générales qu'il avait avant — c'est le signal de ce terme précis, pas un simple "sous-entraînement".
